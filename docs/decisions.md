# Decisions Log

Short record of what was decided and why. Add new decisions at the top.

| Decision | Why |
| --- | --- |
| Implementation Plan v2 (31 Oct 2026) applied to the built server: app routes under **`/v1`** (`/v1/auth/firebase`, `/v1/me`, `/v1/me/photo-upload`, `/v1/me/device`, `/v1/guardians/:id/resend-invite`, …); guardian invite API `/g/i/:code`, live links `GUARDIAN_WEB_URL/l/<code>`. One 90-day session token (no refresh token) and one `/v1/locations` route kept. Test SOS is its own call `POST /v1/sos/test`: accepted guardians only, 5 a day, saved already ended, no link. Real SOS still reaches pending guardians. `POST /v1/sos` takes `simSmsSentTo` (those guardians get only the live link). Profile name 2–50 characters, letters in any language. `GET /v1/me` returns photo link, accepted-guardian count and the safety rules | Owner's choices on the plan review; old app versions keep working under a versioned prefix |
| **Blocking users is removed for now** (pilot has no reason to block). The app server ignores `users.status`; the admin Users screen's Block / Unblock is to be removed by the admin side | Blocking must never stand between a person and an SOS |
| Audio keys stay only on the user's phone (Android Keystore); the server stores only encrypted clips. Only the recording phone can play them; a lost or reset phone means nobody can play them, and a police / court request can only receive the encrypted files | Owner decision 31 Oct 2026: strongest privacy, trade-off accepted |
| Live location (A5): each point carries an id made on the phone (`location_points.client_point_id`, unique per user, migration 0013), so a resent batch is saved once. Points accepted for the user's own SOS / journey while active and up to 2 minutes after it ends; up to 1 day old, at most 1 minute ahead. Redis: newest point per SOS / journey in `loc:last:<sos|journey>:<id>` (only moves forward in time, 24 h expiry); every new point published on `<sos|journey>:<id>:location` (no names or numbers); heartbeat time per user in the sorted set `heartbeats` (for the lost-contact check in Part B) plus battery / network in `hb:<user id>`. The phone's "last seen" is written at most once a minute. `delete_after` stays empty until the client sets a retention period | No duplicates from retries; the live map never jumps back to an old point; Part B and the live pages read fixed Redis names |
| SOS (A4): one active SOS per user (a lock stops two quick presses making two); same phone-made id → same SOS. Who gets a live link: guardians who accepted or have not answered (never declined). Link code random, SHA-256 stored, open while active (`expires_at` = infinity) and until end + `guardian.link_live_after_end_minutes`. Every SOS stores `rules`: a copy of all Settings values at the start (migration 0012); later steps read the copy. Countdown cancels are saved as `status = cancelled`, `end_reason = cancelled_in_countdown`, with no links or messages. Start time accepted up to 1 day old (offline) and at most 1 minute ahead | Owner decision on who is alerted; settings changes never affect a running SOS; false alarms still counted in reports |
| Guardian invites: SMS with a link (random code, only its SHA-256 stored, 7 days, a resend replaces it). Accept / decline without login on `/g/invite/<code>`. Declining deletes the number and keeps only an HMAC-SHA256 of it (`PHONE_HASH_KEY`) per user, so that user can't invite it again (another user still can). Max guardians read from Settings at the time of adding; declined ones don't count. 10 invites (including resends) per user per day, counted before anything is saved. No removing guardians during an SOS | Privacy for people who say no; no spamming; nothing changes mid-emergency |
| Until Part B, outgoing SMS go through `OutgoingMessages`, which only prints them in the server console with the number masked. Invite SMS get an `alerts` row (type `invite`) in Part B, when they are really sent | Develop and test without real SMS or DLT |
| Profile photos: JPEG only, max 2 MB, stored under `users/<user id>/photo/` (the key proves whose photo it is); the old photo is deleted when a new one is saved; the app gets a 1-hour link to show it; 10 upload links per user per hour | Small, private, nothing left behind |
| Phones (`devices`): the app's install id is the row id; if another user logs in on the same phone, the row moves to them; a push token is kept on one phone row only; the login session records its phone. The user's "last seen" is updated at most once a minute | Admin "Setup complete" and device details always show the phone in use; push never goes to the wrong person |
| App login: the phone signs in with Firebase phone OTP; `POST /app/auth/login` checks the Firebase token (`firebase-admin`, sign-in method must be phone), keeps Indian mobiles only, creates the user on first login and returns our own token (`user_sessions`, SHA-256 stored). Token sent as `Authorization: Bearer`. 90 days from last use; **one phone at a time** (a new login ends the old session). Login refused for blocked users, but a blocked user who is already logged in stays logged in so SOS always works. 10 login tries per IP per 15 min. Until the terms are accepted (`consent_at`, `consent_version`), only me / consent / logout work | Confirmed by the owner (27 Oct 2026). Our own session lets us block, log out and expire without calling Firebase on every request |
| `/app` routes have their own login check (`AppAuthGuard`, default deny) and error shape (`AppExceptionFilter`); the admin guards, audit and error replies are untouched | User app and admin panel stay separate |
| Automated tests use a fake Firebase check (`FakePhoneTokenVerifier`, only when `NODE_ENV=test`); real Firebase is tested by hand with Firebase test phone numbers. Without `FIREBASE_PROJECT_ID` app login is off locally (`service_unavailable`); required in production | No Firebase emulator (needs Java) on every computer |
| API contract for the user app: Zod schemas in `packages/shared` (`@sarthi/shared`, built to `dist/` by `pnpm install`), used by the server to check input; the same list written out for Flutter in `docs/app-api.md`. One error shape for `/app` and `/g`: `{ error, message }` with fixed codes | One source of truth for TypeScript; Dart can't read TypeScript, so the app follows the written page |
| Local file storage: **SeaweedFS** (`chrislusf/seaweedfs:4.48`) in Docker, S3 API, port 8333, buckets `sarthi-dev` and `sarthi-test` (made by the server on start, outside production). The server uses the standard S3 API (`@aws-sdk/client-s3`), so production switches to DigitalOcean Spaces by settings only. Storage settings have local defaults outside production and are required in production. Storage being down does not stop the server (a warning only) | MinIO was planned, but it was archived and its Docker image is no longer published. SeaweedFS is open source (Apache 2.0), one container, supports upload links. Defaults keep existing `.env` files working |
| Phones upload files directly with 5-minute upload links; the file type and exact size are signed into the link | The server never streams files; a link can't be reused for a bigger or different file |
| Fake call removed from Phase 1 (27 Oct 2026) | Requested by the project owner; not built unless asked again |
| SOS & Journey History (both roles, read-only): SOS rows show the user (name + masked phone, link to profile); **journey rows never name the person** ("A user's journey"); a person's own journeys are only on their profile. Deleted users show as "Deleted user" with no link | Rule 6 (journeys as counts, not names) applied to lists too |
| History never shows a map or coordinates; location appears only as gaps ("No location for 5 min") when updates stop for **2 minutes or more** (fixed in code) | Rule 6: live location only during an active SOS |
| Outcomes: SOS — Ended safe · Cancelled in countdown · Still active (links to Live SOS); journey — Arrived safely · Ended · Lost contact · Turned into SOS (opens that SOS) | One set of plain names for the filter, list and timeline |
| Timeline guardians appear as "Guardian 1 (brother) +91 98•• ••0001": numbered in the order the user added them, with the relation if the user gave one (new optional `guardians.relation`, migration 0009), masked phone, never the name or full number | Enough for support to follow what happened, without personal details |
| **Blocking a user never blocks SOS.** Blocking stops only login, new journeys and new guardian invites; it never ends an SOS or a journey already running. Block and Unblock need a written reason (both roles), saved in the audit log | A blocked person may still be in danger; blocking must never stop someone getting help |
| Users screen: phone search by the **exact full number only** (no partial search); sent in the request body, never in the web address; logged as a view without the number. Full phone numbers never leave the server (users and guardians are masked, e.g. `+91 98•• ••4521`) | Partial search would let an admin browse numbers; masking (rule 7) is enforced on the server |
| "Setup complete" = location, notifications, SMS and microphone permissions granted + battery saving off for the app + at least one accepted guardian (permission names to be kept in step with the app) | One clear meaning for support staff |
| "Send setup reminder" is shown disabled ("Push notifications are not set up yet") until Firebase is connected | Honest about what works today |
| "Delete data" (Super Admin, written reason): the confirm box lists what is deleted (profile, guardians, journeys, locations, recordings) and what is kept (SOS events and alerts, with no link to the person). Refused while an SOS or journey is running, and while the user has audio recordings (file storage not connected yet) | Never delete in the middle of an emergency; never leave audio files behind |
| Audit Log screen: Super Admin only, read-only (no change, delete or export). Newest first, 50 per page with "Load more". Filters: admin (removed admins included), kind (views and changes / changes only / logins only), India dates. Opening the log is itself logged | Who looked at the log is part of the record |
| Audit tags: **Viewed / Changed / Login**, with a red "Failed" or "Refused" tag where needed (not "Logged in": a failed login or a logout is not a login) | Clear at a glance |
| Audit "Admin" column: "Unknown email" for a login with an email that matches no admin (the typed text is never stored or shown: people sometimes type a password into the email box); "System (server command)" for the setup command | No secrets in the log, but every attempt is visible |
| All admin panel times are India time (Asia/Kolkata), whatever time zone the computer uses; the Details drawer shows the raw browser text (no parsing library) | One clock for the whole team; fewest dependencies |
| Admin Team: "Remove" disables the account (cannot log in, sessions ended); the row stays in the list, greyed at the bottom with a "Removed" tag and no actions. Adding a removed admin's email again **restores the same account** (changed 27 Oct 2026; earlier it was refused): name and role from the form, new temporary password, old password and 2-step wiped, logged as `admin.restored`. Never remove yourself or the last Super Admin | The audit log refers to admins, so their history must stay complete and linked to one account; a person who returns should be easy to add back |
| New admins and password resets get a one-time temporary password (24 h, must be changed), shown once with: "Give this password to the person directly (in person or on a phone call). Don't send it by email or WhatsApp." It is stored only as a hash and never logged | A password sent in writing can be read by others |
| "Reset password" only for Support Admins; it also turns off their 2-step setup, unlocks the account and ends their sessions. Super Admins: `pnpm app:setup --reissue` only. Adding a Super Admin needs an extra confirmation. Role changes are not available (for now) | Fewest ways to gain or take over a Super Admin account |
| SOS countdown is always cancelled without a PIN; fixed in code, not a setting | Speed matters more than a PIN in an emergency; as a fixed rule (`FIXED_RULES` in `server/src/settings/default-settings.ts`) it can never be changed through the API. Migration 0008 removed only its old settings row |
| Settings ranges (whole numbers): SOS countdown 3–10 s · stopped too long 2–15 min · off route 200–2000 m · late arrival 5–60 min · wait for check-in reply 1–5 min · "stuck in traffic" pause 5–30 min · lost contact 3–15 min · no guardian responds 2–10 min · guardian link after SOS ends 5–60 min · audio auto-delete 7–90 days · max guardians 1–5 | Agreed with the project owner; checked on the server (one source: `default-settings.ts`), shown in the panel |
| Settings changes: Super Admin only; a written reason (at least 10 characters) is required; one audit row per changed setting with before/after values in `audit_log.details` (setting names and values only, never phone numbers or names); a save based on an old version is refused (two admins editing at once) | Every change is explained and traceable; nothing is overwritten silently |
| When a settings change applies: new SOS events and journeys only (running ones keep the old rule); audio auto-delete applies to new recordings only; max guardians: users who already have more keep them but can't add more | Changing a rule must never change an emergency that is already happening |
| 2-step login is a switch, `ADMIN_TWO_STEP` (on/off): **off by default in local development**, on by default in test and production; the server **refuses to start** with it off when `NODE_ENV=production` (staging runs as production too). The 2-step code, screens and tests stay | Requested by the project owner: no authenticator app needed while developing locally. **Risk:** on a laptop with 2-step off, a leaked or guessed password alone opens the panel; lockout (5 tries / 15 min), rate limits and auto logout still apply, and local data is not real user data. Staging and production can never run without 2-step, because the panel shows live SOS locations |
| Admin panel: Vite 8, React 19, Ant Design 6 (its own `QRCode` and `Input.OTP`, so no QR or code-input library), React Router 8, TanStack Query 5, React Hook Form + Zod; fonts from `@fontsource` | Stack from CLAUDE.md; fewest extra packages |
| The panel calls the API directly (`VITE_API_URL`, cookies with `credentials: 'include'`), not through a dev proxy | Same cross-origin set-up as production, so CORS and the cookie are tested locally |
| The panel stores nothing about the session in the browser; login state comes only from `GET /admin/auth/me`, checked every minute. Backup codes live only in page memory | Design rule; a stolen browser profile holds nothing useful |
| The server's 401 says why: `no_session`, `idle`, `expired`, `ended` or `login_incomplete` (+ next step). `ended` covers logout, password change, disabled and locked, so nothing about the account is revealed | The login page shows the design's message for each reason; a refreshed login step returns to the same step |
| `/me` is a passive request: it never counts as activity | Otherwise the panel's once-a-minute check would keep every session alive and the 30-minute auto logout would never happen |
| One theme file `apps/admin/src/theme.ts`; it also sets `--sr-*` CSS variables used by `styles.css`. A few colours only in the design page (alert text, map grid, sidebar divider) were added there | No hard-coded colours anywhere else |
| Browser tests (Playwright, Chromium) start their own server and panel on ports 3100 / 5174 with the test database; `pnpm test` runs server tests first, then browser tests, one after the other | Never touch dev servers or dev data; both suites share `sarthi_test` |
| Admin login in steps: password → forced change of a temporary password → 2-step setup or check → full session. A new session ID at every step; a half-finished login can only call the next step | Stops session fixation; nothing is reachable before 2-step is done |
| Sessions in PostgreSQL (`admin_sessions`, token stored as SHA-256), cookie `__Host-sr_admin` (HttpOnly, Secure, SameSite=Strict). Auto logout after 30 min idle, at most 12 h; half-finished login 10 min | Sessions can be ended in the same transaction as a reset; permanent record. Limits fixed in code, not admin-editable |
| 2-step: own RFC 6238 TOTP code (no library, tested against the RFC values), ±30 s drift, each time step usable once; 10 one-time backup codes | Small, well-specified; replay blocked twice (in code and by an atomic database update) |
| One `ADMIN_TOTP_ENCRYPTION_KEY`; HKDF-SHA256 derives two separate keys: AES-256-GCM for authenticator secrets (bound to the admin id), HMAC-SHA256 for backup codes. Every code/hash comparison uses `timingSafeEqual` | Key separation; a leaked database alone cannot be used to read secrets or guess backup codes. Changing the setting invalidates existing 2-step setups |
| Lockout: 5 failures in a row (password or 2-step) lock the account for 15 min; 20 attempts per IP per 15 min (Redis; if Redis is down the IP limit is skipped, the lockout still applies). One reply for every login failure | Slows guessing without revealing which emails exist |
| **Known trade-off:** anyone who knows an admin's email can lock that account for 15 minutes by failing on purpose. `--reissue` (Super Admin) and waiting out the lock are the recovery paths. Production may restrict admin login to an IP allowlist or VPN | Lockout protects against password guessing; the cost is this nuisance risk |
| Strict CORS (only `ADMIN_PANEL_ORIGIN`, with credentials) plus an Origin check and JSON-only bodies on every state-changing /admin request | Defence against cross-site requests on top of SameSite cookies |
| Default deny: every `/admin` route needs a finished login unless marked otherwise; roles are checked on the server (`@Roles`); refused attempts are logged (`auth.access_denied`) | New screens are protected automatically |
| Audit volume: every action and every page/data view by a logged-in admin is logged, with session and result code. Background refreshes (`/me`) are not; the same view (same URL) by the same session is logged at most once per 60 s (tracked in Redis) | Complete record without flooding the table |
| `--reissue` also clears 2-step setup and backup codes, unlocks the account and ends every session. A Super Admin can reset a Support Admin's 2-step through the API (written reason, sessions ended, logged); Super Admins only via `--reissue` | Recovery from a lost phone without weakening the normal path |
| Admin passwords: Node's built-in scrypt, N=2^16, r=8, p=2 (OWASP-listed), maxmem 128 MB, 16-byte salt; stored as `scrypt$N$r$p$salt$hash` | No extra library or native build; settings are stored per hash so they can be raised later |
| First Super Admin via `pnpm app:setup --name --email`: one-time temporary password (20 chars, ~115 bits) shown once in the terminal, never stored or logged; must be changed at first login; expires after 24 hours. Refuses if any Super Admin exists | No password in code or `.env`; only one bootstrap path |
| Break-glass: `pnpm app:setup --reissue --email` gives an EXISTING Super Admin a new temporary password and re-enables the account; never creates an admin; audit-logged (`setup.super_admin_reissued`) | Recovers from an expired temporary password or a disabled only Super Admin. Needs server access, so it is only for the tech lead |
| Default safety settings inserted by the setup command, only if missing. Location retention and SMS providers are not inserted until agreed | Running setup again never undoes a change made in Settings |
| Test database reset by undoing and re-running all migrations (before and after each run, and before each setup test); end-to-end tests run one file at a time | `audit_log` and `sos_events` refuse deletes, so dropping tables is the clean way to wipe; tests never leave records |
| Kysely (0.29) for migrations and typed queries; migrations written as plain SQL | One small tool with no dependencies, on the `pg` driver we already use; plain SQL is easy to review; PostGIS works directly |
| `sos_events`: a database trigger blocks deletes and changes to id, user_id, trigger, is_test, started_at (user_id may only become NULL on account deletion). Status, ended_at, end_reason can change. Admins have no edit API at all | SOS history must be trustworthy, even if application code has a bug |
| `audit_log` is append-only (triggers block UPDATE, DELETE and TRUNCATE) | An audit trail that can be edited proves nothing |
| Production: the server connects as a **limited database user** (read/write rows only: no DDL, no TRUNCATE, not the table owner). Only migrations run as the owner user | Triggers can be dropped or disabled by the table owner; a limited user cannot, so the audit and SOS protections hold even if the server is compromised |
| Guardian API (when built): a declined guardian's row loses its phone; only a **hashed** phone is kept in a "do not invite again" list | Stops repeat invites to someone who said no, without keeping their number |
| "Delete my account" (`deleteUserData`): deletes user, devices, guardians, journeys, location points, check-ins, guardian links, audio clips and support tickets; keeps SOS events and alerts with every link to the person removed | DPDP: personal data goes; anonymous counts keep pilot reports correct. Support tickets are deleted because their messages are personal text |
| Guardians who decline: phone number removed (database rule: a declined guardian must have no phone). The guardian API does this when it is built | Someone who said no should not stay on file |
| `location_points.delete_after` for a future cleanup job; retention days to be agreed with the client and stored as a setting | Location history is sensitive and should not be kept forever |
| Alerts and audit_log hold ids only, never phone numbers or names (including provider error text) | They are kept after account deletion |
| Node.js 24 LTS (≥ 24.9) for the server, locally and on DigitalOcean; Jest runs with `--experimental-vm-modules` | NestJS 12 ships only as ES modules; Jest loads them only on Node ≥ 24.9 with that flag. Node 22 leaves support in April 2027 |
| Server: NestJS 12, TypeScript 6.0 (not 7), `pg` driver, ioredis 5 (not 6), Zod for settings; no `@nestjs/config` or `@nestjs/terminus` | TS 7 not yet supported by ts-jest/typescript-eslint; BullMQ uses ioredis 5; Node's built-in `.env` loader and a small custom `/health` are enough |
| Settings from root `.env` if present, otherwise real environment variables; test URLs required only in development/test | Same code runs locally and on DigitalOcean; tests can never fall back to dev data |
| Local Docker: `postgis/postgis:17-3.5`, `redis:7.4-alpine`; one PostgreSQL container with two databases (`sarthi_dev`, `sarthi_test`); local PostgreSQL port 5433; Redis tests use DB `/1` | Same PostgreSQL version as DigitalOcean managed; pinned versions for everyone; simplest setup that keeps test data separate; 5433 avoids clashing with a Windows-installed PostgreSQL |
| Admin UI design is `docs/design/admin-panel.html` + `docs/admin-design.md`, not Figma; Ant Design in code | No Figma file available; a design page in the repo is one source of truth Claude Code can read directly |
| No fake data in the admin panel; no simulator; clear empty states | Requested by the project owner; only real data and real configuration appear in the panel |
| Local development uses Docker (PostgreSQL + PostGIS, Redis); staging and production use DigitalOcean | Docker is the easiest identical setup for every developer; DigitalOcean hosts the real system in India |
| Build the admin panel first, with the backend it needs | Requested by the team |
| Admin panel: React + Vite + Ant Design (not Next.js) | Panel sits behind a login, needs no search engine pages; Ant Design gives ready admin components |
| Support Admin is not a command centre | Support handles app problems in office hours; emergencies go to guardians and 112 in Phase 1 |
| Excluded for now: auto-call, silent alert, Hindi | Not in the scope document |
| WhatsApp alerts only via Change Request | Not in the scope document |
| Disaster alerts (official NDMA) moved to Phase 2 | Simple, uses official data; replaces crowdsourced earthquake warning |
| Child Safety Mode must be visible (Phase 4) | Hidden monitoring is banned by Google Play and legally risky |
| Admins cannot play audio | Privacy; audio belongs to the user. Export only for police/court requests, logged |
| Audio auto-deletes after 30 days unless kept | Privacy and storage |
| No-guardian-response backup: re-send alerts, help user call 112 | No command centre in Phase 1 |
| Check-ins only on events: off route 500 m, stopped 3 min, late 15 min | Fewer annoying prompts; no reply in 2 min alerts guardians (not full SOS) |
| SOS countdown 5 s, cancel without PIN | Speed; guardians are told if an SOS is cancelled |
| Phase 1 uses "while using the app" location only | Easier Google Play approval; tracking runs in a user-started foreground service |
| Guardians use an SMS web link, no app | Removes the biggest adoption barrier |
| SMS: Indian provider + backup, DLT registered; SIM SMS when offline | Delivery in India; works without internet |
| Firebase for push, crash reports and login OTP | Standard on Android; OTP works before DLT is ready |
| Database: PostgreSQL + PostGIS; Redis + BullMQ | Linked data, location maths, fast live data and timers |

| Stack: Flutter + Kotlin safety engine, Node.js (NestJS), React | Team skills; native code needed for reliable background work |
| Android first, Noida pilot | Most users on Android; team is based in Noida |
